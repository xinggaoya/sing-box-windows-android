# 项目全量重构需求（v2）

更新时间：2026-02-22

## 1. 背景结论（基于现状代码）

当前项目可用，但存在以下结构性问题：

1. `MainActivity` 承担过多编排职责（状态聚合、权限、错误弹窗、业务调用），难维护。
2. 全局单例 `Store + mutableStateOf` 分散在多个模块，状态一致性与测试成本较高。
3. UI 与业务层耦合偏重，页面回调直接触达 `Repository/Manager`，边界不清晰。
4. `libbox.aar` 目前主要依赖手工更新，缺少统一可追溯的自动构建链路。

## 2. 重构目标（不考虑兼容性）

本次重构按“新项目”标准执行，不追求旧代码兼容：

1. **架构重置**：从单模块单例模式，重构为清晰的分层与模块边界。
2. **状态重置**：统一到可测试的单向数据流（UDF/MVI）模型。
3. **UI 重置**：在保留功能的前提下，重新设计交互与视觉层级。
4. **核心链路重置**：统一 VPN、核心生命周期、配置生成、订阅同步的领域边界。
5. **构建链路重置**：内核 AAR 支持自动拉取、自动构建、版本可追溯。

## 3. 功能基线（v2 必须覆盖）

1. VPN 连接控制（连接、断开、状态反馈）。
2. 订阅管理（新增、编辑、删除、激活、同步、本地导入）。
3. 节点组与节点选择（含延迟测试）。
4. 实时流量与核心状态展示。
5. 设置管理（DNS、路由、Clash API 等核心选项）。
6. 应用更新检查与下载。

## 4. 新架构方案（目标形态）

建议改为多模块（或先逻辑分层后模块化）的结构：

1. `app`：仅保留壳层、导航、依赖装配。
2. `core:model`：纯数据模型与协议定义。
3. `core:common`：日志、错误模型、结果封装、时间与调度抽象。
4. `domain:*`：用例层（连接、订阅、节点、设置、诊断）。
5. `data:*`：本地存储、网络访问、配置转换、核心接口实现。
6. `feature:*`：按页面拆分（home/subscription/nodes/settings/diagnostics）。
7. `platform:vpn`：`VpnService` 与 Android 平台能力桥接。
8. `platform:core`：`libbox` 生命周期与命令接口适配。
